# La CI (`.github/workflows/ci.yml`) — pour un débutant complet

> Ce fichier est indépendant du reste du tour (`01-overview.md` → `10-protocol.md`, qui expliquent le
> code de l'app). Il explique un fichier différent : `.github/workflows/ci.yml`, qui ne fait pas partie
> du programme Lito lui-même — c'est de la configuration pour **GitHub**, le service qui héberge le
> dépôt. Aucune connaissance de Rust ou de Slint n'est nécessaire pour suivre ce document.

---

## C'est quoi, la CI, et à quoi ça sert ?

CI veut dire **Continuous Integration** (intégration continue). L'idée : à chaque fois que du code
change (un `git push`, une pull request), une machine — pas la tienne, une machine dans le cloud —
recompile le projet et fait tourner les vérifications automatiquement, sans qu'un humain ait besoin d'y
penser.

Avant la CI (voir `roadmap.md`, item P0.2), ce projet avait quatre commandes utiles dans son
`Makefile` (`make fmt`, `make clippy`, `make test`, `make ui-check`) mais **rien ne forçait
personne à les lancer**. Il suffisait d'oublier une fois pour pousser du code mal formaté, ou pire, du
code qui ne compile pas. La CI ferme cette faille : elle relance ces mêmes vérifications toute seule,
et affiche un ✅ ou un ❌ bien visible sur chaque commit et chaque pull request. Un ❌ n'empêche rien
par défaut (aucune règle de blocage n'est configurée sur `main` dans ce dépôt) mais c'est un signal
immédiat que quelque chose est cassé, avant qu'un humain le découvre en récupérant le code.

**Ce que la CI ne fait pas** : elle ne déploie rien, n'installe rien chez l'utilisateur final, ne
publie pas de release. Ici, elle se contente de *vérifier* (compiler, tester, formater) — c'est
volontairement le scope le plus simple possible pour commencer (voir P5.5 dans `roadmap.md` pour un
futur processus de release, qui est une préoccupation différente).

## GitHub Actions : le vocabulaire de base

Ce projet utilise **GitHub Actions**, le système de CI intégré à GitHub (il en existe d'autres :
GitLab CI, CircleCI, Jenkins... le vocabulaire ci-dessous est propre à GitHub Actions, mais les
concepts se retrouvent presque partout ailleurs sous d'autres noms).

| Terme | Ce que c'est |
|-------|--------------|
| **Workflow** | Un fichier YAML qui décrit "quoi faire, et quand". Ici : `.github/workflows/ci.yml`. Un dépôt peut avoir plusieurs workflows (un pour la CI, un autre pour publier une release, etc.) — chacun est un fichier séparé dans `.github/workflows/`. |
| **Trigger** (déclencheur) | L'événement qui démarre le workflow — un `push`, l'ouverture d'une pull request, un planning (cron), un déclenchement manuel... |
| **Job** | Une unité de travail indépendante à l'intérieur d'un workflow, exécutée sur **sa propre machine virtuelle**. Un workflow peut avoir plusieurs jobs, qui tournent en parallèle par défaut. |
| **Step** (étape) | Une action précise à l'intérieur d'un job — "installer Rust", "lancer telle commande"... Les steps d'un même job s'exécutent dans l'ordre, l'un après l'autre, sur la même machine. |
| **Runner** | La machine virtuelle (fournie et détruite par GitHub) sur laquelle un job s'exécute. Éphémère : elle est recréée toute neuve à chaque run, puis jetée à la fin. |
| **Artifact** | Un fichier produit pendant un job, que GitHub garde et rend téléchargeable après coup (ici : les captures d'écran de l'UI, voir plus bas). |

Une image mentale utile : un **workflow** est une recette, chaque **job** un plat de cette recette
préparé dans sa propre cuisine (le **runner**) en même temps que les autres plats, et chaque **step**
une instruction de la recette pour ce plat précis, à suivre dans l'ordre.

## Le fichier, étape par étape

Voici `.github/workflows/ci.yml` tel qu'il existe dans ce dépôt :

```yaml
name: CI

on:
  push:
  pull_request:

jobs:
  check:
    runs-on: macos-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install Rust
        run: rustup component add rustfmt clippy
      - uses: Swatinem/rust-cache@v2
      - name: cargo fmt --check
        run: cargo fmt --all -- --check
      - name: cargo clippy
        run: cargo clippy --workspace -- -D warnings
      - name: cargo test
        run: cargo test --workspace
      - name: cargo build --release
        run: cargo build --release

  ui:
    runs-on: macos-latest
    steps:
      - uses: actions/checkout@v4
      - uses: Swatinem/rust-cache@v2
      - name: Install slint-viewer
        run: cargo install slint-viewer --version "^1.17" --locked
      - name: make ui-check
        run: make ui-check
      - name: make ui-shot
        run: make ui-shot
      - name: Upload UI screenshots
        uses: actions/upload-artifact@v4
        with:
          name: ui-shots
          path: target/ui-shots/*.png
```

### `name: CI`

Juste une étiquette lisible par un humain — c'est ce nom qui apparaît dans l'onglet "Actions" de
GitHub et à côté de chaque commit.

### `on: push` / `pull_request`

Les **triggers**. Ce workflow se déclenche sur **tout** `push` (peu importe la branche) et sur toute
mise à jour d'une pull request. Rien d'autre n'est filtré ici (pas de restriction à `main`, pas de
planning) — volontairement simple pour un projet à ce stade.

### `runs-on: macos-latest`

Chaque job précise sur quel type de machine il tourne. Ici, `macos-latest` — une vraie machine macOS
fournie par GitHub, pas Linux ni Windows. C'est un choix imposé par le projet : Lito compile une UI
Slint et un `.app` bundle macOS (voir `CLAUDE.md`), donc il **doit** être compilé et testé sur macOS
pour que ça ait un sens (les runners macOS sont aussi plus chers en minutes que Linux/Windows — voir
la note sur le coût, plus bas).

### `steps` — dans l'ordre, sur la même machine

Chaque step a soit `uses:` (réutilise une **action** déjà écrite par quelqu'un d'autre — un bout de
code publié sur GitHub, référencé par `propriétaire/nom-du-repo@version`), soit `run:` (exécute
littéralement une commande shell, comme si tu la tapais toi-même dans un terminal sur cette machine).

- **`actions/checkout@v4`** — la toute première étape de presque n'importe quel job GitHub Actions : le
  runner démarre avec un disque vide, cette action clone le dépôt dessus. Sans elle, il n'y a
  littéralement aucun code à compiler.
- **`rustup component add rustfmt clippy`** — les runners `macos-latest` de GitHub ont déjà Rust
  préinstallé, mais pas forcément les composants `rustfmt` (le formateur) et `clippy` (le linter)
  utilisés plus bas ; cette ligne les ajoute.
- **`Swatinem/rust-cache@v2`** — voir la section dédiée juste en dessous.
- Les quatre lignes suivantes (`cargo fmt --all -- --check`, `cargo clippy --workspace -- -D
  warnings`, `cargo test --workspace`, `cargo build --release`) sont **exactement** les commandes
  `make fmt`/`make clippy`/`make test`/`make build` du `Makefile` — la CI ne réinvente rien, elle
  relance ce qui existait déjà, mais automatiquement et sur une machine propre à chaque fois. Le seul
  écart volontaire : `cargo fmt --all -- --check` plutôt que `make fmt` (`cargo fmt --all` tout court)
  — `--check` fait **échouer** la commande si le code n'est pas déjà formaté, au lieu de le reformater
  sur place. Reformater automatiquement en CI n'aurait aucun sens : le runner est jeté à la fin du job,
  ce changement ne serait jamais renvoyé nulle part.

### Le job `ui`

Un second job, indépendant du premier (il tourne sur sa propre machine, en parallèle de `check`). Il
installe `slint-viewer` (l'outil qui sait afficher un fichier `.slint` sans lancer toute l'app —
voir `03-slint-ui.md`), puis relance `make ui-check` et `make ui-shot`, exactement comme un humain le
ferait sur son propre Mac avant de proposer un changement visuel (voir `CLAUDE.md`, section "UI
architecture").

### `actions/upload-artifact@v4`

`make ui-shot` produit des fichiers PNG dans `target/ui-shots/` — mais ce dossier vit **sur le
runner**, qui est détruit à la fin du job. Sans cette étape, ces images seraient perdues et
personne ne pourrait les regarder. `upload-artifact` les copie ailleurs, dans le stockage de GitHub,
sous le nom `ui-shots` ; elles apparaissent ensuite comme fichiers téléchargeables en bas de la page
du run, dans l'onglet "Actions" — ce qui permet de relire visuellement un changement d'UI directement
depuis une pull request, sans avoir à récupérer la branche et lancer `make ui-shot` soi-même.

## Pourquoi les deux jobs sont séparés

`check` et `ui` auraient pu être un seul job avec toutes les étapes à la suite. Ils sont séparés pour
deux raisons concrètes :
1. **Ils tournent en parallèle** (deux runners distincts démarrent en même temps) plutôt qu'en série —
   le résultat global arrive plus vite.
2. **Un échec dans l'un n'empêche pas de voir le résultat de l'autre.** Si `make ui-shot` casse à
   cause d'un bug dans `slint-viewer`, ça n'empêche pas de savoir si les tests Rust, eux, passent
   toujours — et vice-versa.

## Le cache : `Swatinem/rust-cache@v2`

Compiler ce workspace Rust en partant de zéro (aucune dépendance déjà téléchargée ni compilée) prend
plusieurs minutes — et un runner GitHub Actions démarre justement **de zéro** à chaque fois, disque
vide compris. Sans rien pour compenser, chaque run recompilerait donc l'intégralité des dépendances du
projet, à chaque push.

`Swatinem/rust-cache@v2` sauvegarde, à la fin du job, les dossiers que Cargo (l'outil de build de
Rust) utilise pour stocker les dépendances déjà téléchargées et déjà compilées (`~/.cargo` et
`target/`) — puis les restaure en tout début du run suivant, à condition que `Cargo.lock` n'ait pas
changé depuis. Le run suivant ne recompile alors que le code de *ce* projet, pas ses dépendances
externes.

## Pourquoi `crates/llm::test_ollama_client` est marqué `#[ignore]`

Un des tests du projet vérifie qu'`OllamaClient` sait parler à un vrai serveur Ollama :

```rust
#[test]
#[ignore]
async fn test_ollama_client() {
    let client = OllamaClient::new("http://localhost:11434", "qwen3.5:4b");
    assert!(client.health_check().await);
}
```

Ce test suppose qu'un serveur Ollama tourne déjà sur `localhost:11434`, avec le modèle
`qwen3.5:4b` déjà téléchargé — vrai sur la machine d'un développeur qui a Ollama installé, jamais vrai
sur un runner GitHub Actions (une machine vierge, jetée après le job, qui n'a jamais entendu parler
d'Ollama). Sans l'annotation `#[ignore]`, `cargo test --workspace` échouerait **à chaque run de CI**,
pas parce que le code est cassé, mais parce que l'environnement de test n'a pas ce dont ce test a
besoin.

`#[ignore]` dit à Cargo : "ce test existe, mais ne le lance pas par défaut". `cargo test --workspace`
(ce que la CI exécute) le saute silencieusement ; pour le lancer explicitement, sur une machine qui a
bien Ollama, il faut demander `cargo test -p lito-llm -- --ignored`. C'est un compromis temporaire :
la vraie solution (un faux serveur HTTP qui imite les réponses d'Ollama, pour que le test tourne
partout sans dépendance externe) est notée comme prochaine étape dans `summary.md` et dans
`roadmap.md` (item P0.4).

## Reproduire la CI en local : `make ci`

Attendre qu'un push déclenche la CI pour découvrir qu'un test échoue est lent. `make ci` (ajouté dans
le `Makefile` en même temps que ce workflow) relance exactement les commandes du job `check`, dans le
même ordre, sur ta propre machine :

```bash
make ci
# ≡ cargo fmt --all -- --check
#   cargo clippy --workspace -- -D warnings
#   cargo test --workspace
#   cargo build --release
```

S'il passe en local, le job `check` passera sur GitHub (même code, mêmes commandes — seule la machine
change). Le job `ui` n'a pas d'équivalent `make` unique car il dépend d'un outil externe
(`slint-viewer`) : lance `make install-viewer` une fois, puis `make ui-check`/`make ui-shot` pour le
reproduire.

## Où voir le résultat, et combien ça coûte

Une fois le dépôt poussé sur GitHub : onglet **Actions** du dépôt pour la liste de tous les runs
passés, avec le détail de chaque job/step et les logs complets ; un ✅/❌ apparaît aussi directement
à côté de chaque commit et en bas de chaque pull request.

GitHub Actions est gratuit pour un dépôt **public**, sans limite de minutes. Pour un dépôt **privé**
sur le plan gratuit de GitHub, il y a un quota de minutes par mois — et les runners macOS comme ceux
utilisés ici comptent **10 minutes de quota pour 1 minute réelle** (macOS coûte plus cher à GitHub
que Linux). Un run de ce workflow prenant de l'ordre de quelques minutes, ça reste largement gérable
pour un usage personnel, mais ce n'est pas "illimité" comme en public.
